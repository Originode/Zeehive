# Decision Record: Compose files are ZEEHIVE-generated projections; machine config stays in the meta-DB

**Date:** 2026-08-11
**Author:** Architect (machine-aware-pooling-is-disabled-local-mard-eccb04), directed by the operator:
*"machine configurations should live in meta-db, not structural. compose files should be generated
by zeehive, with the ability to onboard existing compose files for new projects. and at the end of
the day, without zeehive, the compose files should still be workable. but while zeehive still
authors the project, it should treat the compose files as autogenerated content."*
**Status:** Implemented (lib/compose-gen.js, generated docker-compose.spinoff.yml, zeehive.yml
spinoff→compose, provision/build changes; tests compose-gen + provision-compose-spinoff).
**Supersedes in part:** the Option-B rejection in
[`process-machine-pooling-decision-record.md`](process-machine-pooling-decision-record.md) —
Zeehive's spinoff tier now DOES convert to containers, because that is the only door to the
operator's standing ask (Zeehive xells provisioned on other machines) and the compose-authorship
model removes the cost that rejection was priced on (a hand-maintained compose fork).

## Decision

1. **Machine configuration is meta-DB data, never file content.** Which machines exist, their
   contexts/IPs, per-project pool sizes and priorities live in `machine`/`machine_pool` (023/025/
   038) — unchanged, restated as law. A generated compose file carries NO machine fact, which is
   exactly what lets the SAME file run on any daemon via `docker --context`: placement is a
   runtime choice of the pool, not a property of the file.
2. **A project's spinoff compose is a PROJECTION ZEEHIVE generates** (`lib/compose-gen.js`) from
   `zeehive.yml` + naming: services named BY ROLE (the `build-container.sh` contract), every
   parameter interpolated with a default so the file is **standalone-runnable without the
   harness** (`SPINOFF_SLUG=demo docker compose -f docker-compose.spinoff.yml up`), the tier's
   declared env (Zeehive: the §6.2 simulate-safety set) baked in so it is safe even outside the
   harness.
3. **Ownership lives in the file**: the first line carries `# GENERATED by ZEEHIVE`. A marked
   file is ZEEHIVE's to regenerate freely (`POST /projects/:id/compose/generate`, write-refusal
   on drift-free regen); ANY compose without the marker is the project's own — onboarding keeps
   absorbing those (spec §3.1) and `writeGeneratedCompose` refuses to touch them. The marker
   survives clones and needs no DB column.
4. **Zeehive itself converts**: `tiers.spinoff` is now a compose tier over the generated file;
   `runner: process` is gone from the manifest. A Zeehive xell's app tier becomes a per-xell
   stack (nested queenzee + web + own meta-DB), placeable on any configured machine — the
   structural reason "other machines are not provisioning xells" and the dimmed prio/pool knobs
   both end when the manifest cache is refreshed.

## Options considered

- **Hand-authored spinoff compose** (what I was building when the operator redirected). Rejected:
  it is a second copy of shape the manifest already declares — the duplication §2 of the spec
  exists to kill; it rots the day ports/naming/roles change.
- **Generate at build time only, never into the repo.** Rejected: it breaks "without zeehive the
  compose files should still be workable" — the file must travel with branches and clone away
  with the repo; a build-time temp file dies with the harness.
- **Machine facts in the compose file** (per-machine variants). Rejected: house rule 7 in a new
  place; N machines would mean N files that only agree by coincidence; `--context` already
  parameterizes placement at zero file cost.

## Migration (running fleet, live xells)

- **The row outranks the manifest** (build.js): a process-era row (image_tag NULL, docker_ctx
  NULL) keeps its process build under the new manifest; only newly-provisioned xells build as
  containers. The cutover is per-xell, not a fleet-wide cliff — no live xell is stranded.
- **Activation is the manifest refresh** (human, console → Project setup → Manifest → ↻ Refresh
  from repo), after this lands and ships. Until then the fleet's cached manifest keeps the
  process era exactly as-is. After refresh: new pool fills provision machine-placed rows; old
  pooled xells rotate out through the normal reconcile/decommission cycle (or trim the pool once).
- **Per-xell db**: provision inserts the ROW (TCP conn_ref — a spin stack's compose network is
  not zee-hive-net, so a name-based DSN would resolve for nobody); the container comes up with
  the stack at first `zee build`. It starts EMPTY and self-migrates (manifest
  `db.boot_migrations` — the nested queenzee migrates itself at boot); the process-era
  prod-data seed does not carry over — `zee db-catchup --restore` is the data path. Named
  regression, accepted for v1 of remote placement.
- **Remote builds**: `docker --context` streams the worktree as build context to the remote
  daemon; `can_build`/registry knobs (already shipped) route heavy compiles to build-capable
  machines with registry handoff.

## Reversibility

Revert `zeehive.yml` (restore `runner: process`) + refresh: new xells provision as processes
again, and existing container-era xells keep working through the same row-outranks-manifest rule
in the other direction. The generator and marker cost nothing while unused. One-way door: none —
the generated file can even be deleted; regeneration reproduces it byte-identically (the
compose-gen test pins that).

## What would change our mind

A project whose spinoff shape compose cannot express from manifest facts (sidecars, devices,
GPU reservations) — that is the point to extend the manifest schema or hand the file to the
project (drop the marker, onboard it), not to hand-edit a generated file.
